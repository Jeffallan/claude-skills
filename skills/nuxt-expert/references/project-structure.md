# Project Structure, Configuration and Upgrades

Nuxt 4 (current minor 4.6, November 2026) separates browser-and-server app code (`app/`), server-only code (`server/`) and code both sides import (`shared/`). Each context gets its own TypeScript project, so a server import in a component fails type-checking instead of leaking into the client bundle.

## When to Use

- Scaffolding a new Nuxt app or adding a page, layout, middleware, plugin or module
- Deciding where a file belongs (`app/utils` vs `server/utils` vs `shared/utils`)
- Reading or changing `nuxt.config.ts`, `app.config.ts` or layers
- Upgrading from Nuxt 3, or testing Nuxt 5 behavior early

## When Not to Use

- Data fetching details: `data-fetching.md`
- Server handlers: `server-routes.md`
- Rendering modes and route rules: `rendering.md`

## Directory Layout

```text
my-app/
├─ app/
│  ├─ app.vue                # root component (<NuxtLayout><NuxtPage /></NuxtLayout>)
│  ├─ app.config.ts          # public, build-time config (theme, feature toggles)
│  ├─ error.vue              # full-page error screen
│  ├─ assets/                # processed by Vite (CSS, images imported in code)
│  ├─ components/            # auto-imported; `base/Button.vue` -> <BaseButton>
│  ├─ composables/           # auto-imported (top-level files only)
│  ├─ layouts/               # default.vue, admin.vue
│  ├─ middleware/            # route middleware; `*.global.ts` runs on every route
│  ├─ pages/                 # file-based routes
│  ├─ plugins/               # run when the Vue app is created; `.client`/`.server` suffixes
│  └─ utils/                 # auto-imported helpers for app code
├─ server/
│  ├─ api/                   # /api/* handlers
│  ├─ routes/                # handlers without the /api prefix (sitemap.xml, feeds)
│  ├─ middleware/            # runs before every server request
│  ├─ plugins/               # Nitro plugins (hooks, startup)
│  └─ utils/                 # server-only helpers (DB clients, auth checks)
├─ shared/
│  ├─ types/                 # types used by app and server
│  └─ utils/                 # pure functions used by both (no Vue, no Node APIs)
├─ public/                   # served as-is at /
├─ layers/                   # local layers, auto-registered
├─ modules/                  # local modules, auto-registered
├─ nuxt.config.ts
└─ tsconfig.json             # one file; references .nuxt/tsconfig.{app,server,shared,node}.json
```

```json
// tsconfig.json (generated by `npm create nuxt@latest`)
{
  "files": [],
  "references": [
    { "path": "./.nuxt/tsconfig.app.json" },
    { "path": "./.nuxt/tsconfig.server.json" },
    { "path": "./.nuxt/tsconfig.shared.json" },
    { "path": "./.nuxt/tsconfig.node.json" }
  ]
}
```

Rules of placement:

| Code | Folder | Why |
| --- | --- | --- |
| Uses Vue, composables, `window` | `app/` | Bundled for browser and SSR |
| Uses DB clients, secrets, `node:` APIs | `server/` | Never reaches the client bundle |
| Zod schemas, DTO types, formatters | `shared/` | Imported by both via `#shared` |

```ts
// shared/types/product.ts
export interface Product {
  id: number
  name: string
  description: string
  priceCents: number
}
```

```ts
// shared/utils/schemas.ts
import { z } from 'zod'

export const productInput = z.object({
  name: z.string().min(1).max(200),
  description: z.string().max(5000).default(''),
  priceCents: z.number().int().nonnegative(),
})
export type ProductInput = z.infer<typeof productInput>
```

A v3-style project (no `app/` folder) still works: Nuxt detects it. To keep that layout deliberately, set `srcDir: '.'` and `dir: { app: 'app' }`. Do not move files unasked; run `npx codemod@latest nuxt/4/file-structure` when the user wants the migration.

## Routing

```text
app/pages/
├─ index.vue                 # /
├─ about.vue                 # /about
├─ products/
│  ├─ index.vue              # /products
│  └─ [id].vue               # /products/:id
├─ blog/[...slug].vue        # /blog/* catch-all
├─ [[locale]]/contact.vue    # optional param: /contact and /fr/contact
└─ (marketing)/pricing.vue   # route group: /pricing, folder not in the URL
```

```vue
<!-- app/pages/products/[id].vue -->
<script setup lang="ts">
definePageMeta({
  layout: 'shop',
  middleware: ['auth'],
  validate: route => /^\d+$/.test(String(route.params.id)),
})

const route = useRoute()
</script>

<template>
  <ProductDetail :id="Number(route.params.id)" />
</template>
```

`validate` returning `false` renders a 404 without running the page. Typed route names (`useRoute('products-id')`, `navigateTo({ name: 'products-id' })`) need `experimental.typedPages`, which `future.compatibilityVersion: 5` turns on.

## Layouts

```vue
<!-- app/layouts/panel.vue -->
<script setup lang="ts">
defineProps<{ title?: string; sidebar?: boolean }>()
</script>

<template>
  <div class="panel">
    <aside v-if="sidebar"><PanelNav /></aside>
    <main>
      <h1 v-if="title">{{ title }}</h1>
      <slot />
    </main>
  </div>
</template>
```

```ts
// in a page: typed layout props (Nuxt 4.4+)
definePageMeta({ layout: { name: 'panel', props: { sidebar: true, title: 'Dashboard' } } })
```

Set a layout for a whole section in config instead of every page:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: { '/admin/**': { appLayout: 'panel' } }, // Nuxt 4.3+
})
```

## Route Middleware

```ts
// app/middleware/auth.ts
export default defineNuxtRouteMiddleware((to) => {
  const { loggedIn } = useUserSession() // nuxt-auth-utils; see security.md
  if (!loggedIn.value) {
    return navigateTo({ path: '/login', query: { redirect: to.fullPath } })
  }
})
```

Route middleware runs in the Vue app (on the server for the first request, then in the browser). It guards navigation for UX only; the API handler must check the session again (`security.md`).

## Plugins

```ts
// app/plugins/api.ts
export default defineNuxtPlugin({
  name: 'api',
  setup() {
    const config = useRuntimeConfig()
    const api = $fetch.create({
      baseURL: config.public.apiBase,
      onResponseError({ response }) {
        if (response.status === 401) void navigateTo('/login')
      },
    })
    return { provide: { api } } // useNuxtApp().$api
  },
})
```

Prefer `createUseFetch` (`data-fetching.md`) over a provided `$api` when components need SSR-safe fetching with shared defaults.

## Configuration

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  compatibilityDate: '2026-10-01',
  devtools: { enabled: true },
  modules: ['@nuxt/eslint', '@nuxt/image', '@nuxt/ui', '@pinia/nuxt', 'nuxt-auth-utils'],
  css: ['~/assets/css/main.css'],

  runtimeConfig: {
    databaseUrl: '',            // NUXT_DATABASE_URL, server only
    stripeSecretKey: '',        // NUXT_STRIPE_SECRET_KEY, server only
    public: {
      apiBase: '/api',          // NUXT_PUBLIC_API_BASE, sent to the browser
    },
  },

  routeRules: {
    '/': { prerender: true },
    '/admin/**': { ssr: false },
  },

  typescript: { typeCheck: false }, // run `nuxt typecheck` in CI instead of on every dev reload
})
```

| Setting | Read with | Changes at runtime | Holds secrets |
| --- | --- | --- | --- |
| `runtimeConfig` (top level) | `useRuntimeConfig()` on the server | Yes, via `NUXT_*` env | Yes |
| `runtimeConfig.public` | `useRuntimeConfig().public` anywhere | Yes, via `NUXT_PUBLIC_*` | Never |
| `app.config.ts` | `useAppConfig()` anywhere | No, bundled at build | Never |

Keys under `runtimeConfig.app*` are reserved for Nuxt (`appSecret`, `app.baseURL`).

## Modules

Install with `npx nuxt module add <name>`, which adds the dependency and the `modules` entry.

| Module | Version (Nov 2026) | Use for |
| --- | --- | --- |
| `@nuxt/ui` | 4.x | Component library on Tailwind CSS 4 and Reka UI; wrap the app in `<UApp>` |
| `@nuxt/image` | 2.x | `<NuxtImg>`/`<NuxtPicture>` with provider optimization |
| `@nuxt/content` | 3.x | Markdown and data collections queried with `queryCollection` |
| `@nuxt/fonts` | 1.x | Self-hosted web fonts with fallbacks |
| `@nuxt/scripts` | 1.x | Third-party scripts loaded with consent and performance triggers |
| `@nuxt/eslint` | 1.x | Flat ESLint config generated from the project |
| `@pinia/nuxt` | 1.x | Pinia 4 stores with SSR state transfer |
| `@nuxtjs/i18n` | 10.x | Localized routes and messages |
| `nuxt-auth-utils` | 0.6.x | Sealed-cookie sessions and OAuth (needs Nuxt 4.6+) |
| `nuxt-security` | 2.x | Security headers, CSP nonces, rate limiting |
| `@nuxt/test-utils` | 4.x | Vitest environment and e2e helpers |

Before adding a module, check its compatibility field for Nuxt 4 on nuxt.com/modules and its last release date. A module that imports `h3` or `nitropack` directly will need an update for Nuxt 5; one written against `nuxt/server` will not.

## Layers

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  extends: ['github:acme/nuxt-base-layer#v2', './layers/admin'],
})
```

A layer is a Nuxt project whose `app/`, `server/`, config and modules merge into the app. Use them to share a design system or auth setup across apps. Local folders under `layers/` register automatically. In Nuxt 4, layer modules load before project modules.

## Upgrading Nuxt 3 to 4

```bash
npx nuxt upgrade --dedupe
npx codemod@latest nuxt/4/migration-recipe
npx nuxt typecheck
```

Changes that break code most often:

| Nuxt 3 code | Nuxt 4 behavior | Fix |
| --- | --- | --- |
| `data.value === null` checks | `data`/`error` default to `undefined` | Check `!data.value` or `status` |
| Mutating `data.value.items.push()` and expecting re-render | `data` is a `shallowRef` | Replace the value, or `deep: true` |
| Two `useFetch` calls with one key but different `transform` | Same key shares refs; dev warning | Different keys, or the same options |
| `pending` while `immediate: false` | `pending` only during a request | Use `status` |
| `dedupe: true` | Removed | `dedupe: 'cancel'` or `'defer'` |
| `window.__NUXT__` | Removed | `useNuxtApp().payload` |
| `generate: { routes }` | Removed | `nitro.prerender.routes` or top-level `prerender` |
| `createError({ statusCode })` | Deprecated since 4.3 | `createError({ status, statusText })` |
| Server type errors after upgrade | `noUncheckedIndexedAccess` in server tsconfig | Handle `undefined` index results |

Each data-layer change has a revert flag under `experimental` (`granularCachedData`, `purgeCachedData`, `pendingWhenIdle`, `normalizeComponentNames`). Use them only as a bridge and leave a TODO.

## Preparing for Nuxt 5

Nuxt 5 (Nitro 3, h3 2) is scheduled but not released as of November 2026. Nuxt 4 stays supported for six months after it ships. Test the new defaults now:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  future: { compatibilityVersion: 5 },
})
```

The flag turns on, among others: case-sensitive routing, typed pages and typed `$fetch`, `navigateTo` early return, inline error rendering, no Nitro auto-imports in `server/` (import from `nuxt/server`), and env-var runtime config typed to the default value's type. Every item can be toggled one by one under `experimental`. Code that imports server helpers from `nuxt/server` today (`server-routes.md`) runs unchanged on Nuxt 5.

## Common Mistakes

- Putting `server/` inside `app/`: server code must sit at the project root
- Importing from `~/server/...` in a component: use `shared/` for code both sides need
- Defining secrets in `app.config.ts`: it ships to every visitor
- Auto-import surprises: only top-level files in `composables/` and `utils/` are scanned; re-export nested files from an `index.ts`
