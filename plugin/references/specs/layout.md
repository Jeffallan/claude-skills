# Spec Layout

Where the workflow commands keep specs, discovery topics and review files, how they link to each other, and when they move. Every command that reads or writes under the specs root follows this file.

## The specs root

The root is `specsRoot` in `.claude/workflow-config.json`, default `docs/specs`. This file writes paths with the default; commands substitute the configured root everywhere, including in `git mv` commands, launch commands and subagent briefs. Every path is relative to the repo root. Never write a machine-local path into a spec file or a ticket.

```
docs/specs/                             # specsRoot
├── INDEX.md                            # generated by `guard spec-index`, never edited by hand
├── todo/
│   ├── discovery/
│   │   └── <topic>/                    # a discovery topic
│   │       ├── discovery.md            # feature list, open questions, proposed tickets, status
│   │       ├── <feature>.md            # only when Feature Forge ran for that feature
│   │       ├── synthesis.md            # only when research ran
│   │       └── sources/                # only when research ran: interview notes, spike results
│   └── <spec-name>/                    # a spec: a folder with overview.md
│       ├── overview.md                 # header lines first, then the Readiness table
│       ├── implementation-plan.md      # Completion Status table, Proposed tracker changes, open questions
│       ├── goal-prompt.md              # per-run content for /goal
│       └── review/
│           ├── metrics.md              # `guard metrics`, before the reviewer panel
│           ├── <reviewer>.md           # one file per reviewer subagent
│           ├── repro/                  # frozen reproductions from the verifiers, with digests
│           ├── rollup.md               # `guard rollup`, from the verifier verdicts
│           └── pr-feedback-<round>.md  # only when the spec PR got review feedback
└── completed/                          # same shape as todo/
```

Discovery topics sit under `todo/discovery/` and `completed/discovery/`, outside any spec, because specs don't exist until `spec:triage` runs and one topic can feed several specs. `guard spec-index` reads every folder under `discovery/` as a topic and every other folder under `todo/` or `completed/` as a spec, which must hold an `overview.md`. A spec-level folder without one draws a warning and stays out of the index; it is never read as a topic. Never put a topic beside the specs.

`todo/` holds specs that are planned or in progress. Whether a spec has started shows in its Completion Status table, never in its folder.

## Names

Spec names and topic names are kebab-case: lowercase letters, numbers and hyphens. A spec name is used unchanged for its folder, its branch (`spec/<spec-name>`) and its tracker group title. A branch name never contains a tracker ID.

## Links use names, never paths

Tickets, overviews and plans refer to a spec or a topic by name:

```
Spec: <spec-name>
Discovery: <topic>
```

A command that resolves a name looks in `todo/<name>/` first, then `completed/<name>/`. A path written into a ticket would break the first time the spec moves, and the tracker would keep the dead link.

## Overview header lines

The four lines sit above the first `##` heading of `overview.md`. Plain or bold labels both work; values are comma-separated; write `none` when there are no values.

```
**Spec:** <spec-name>
**Discovery:** <topic>, <topic>
**After:** <spec-name>
**Feature areas:** <area>, <area>
```

| Line | Holds | Written by |
|------|-------|------------|
| `Spec:` | The spec's own name; it must match the folder | `spec:create` |
| `Discovery:` | Topics this spec came from | `spec:create`, from the tickets' discovery links |
| `After:` | The spec that must merge first (triage's build order) | `spec:create`, copied from the group's `After:` line |
| `Feature areas:` | Areas of the product this spec changes | `spec:create` |

Keep any other header lines (status, repo, dates) on their own lines; the index ignores them. Never put prose in brackets on a header line, since the index splits values on commas.

## The spec index

`docs/specs/INDEX.md` lists every spec in `todo/` and `completed/` with its status, discovery topics, feature areas and predecessors. Nobody edits it by hand.

```bash
guard spec-index            # write INDEX.md
guard spec-index --check    # write nothing; exit 1 when stale or a name link is broken
```

It fails when a `Spec:` line is missing or doesn't match its folder, when an `After:` name isn't a spec, or when a `Discovery:` name isn't a topic. Run it in the same commit as any change to an overview's header lines or any move between `todo/` and `completed/`. `spec:create` reads the index to find earlier specs and topics on the same feature areas.

## Moves

Every move is a `git mv` in a commit on the spec branch, so the merge carries it to the default branch. The default branch never gets a direct commit. Each move first runs `mkdir -p` on the target's parent folder: `git mv` fails when it is missing, as it is for a repo's first completed spec. Git tracks no empty folders, so a folder emptied by a move disappears from the repo.

| Move | Command | When |
|------|---------|------|
| `todo/<spec-name>` to `completed/<spec-name>` | `spec:complete` | In the completion commit, before the PR opens |
| `completed/<spec-name>` back to `todo/<spec-name>` | `spec:complete` | Review feedback arrived after the move; it commits the move back before printing the fix-round launch commands |
| `todo/discovery/<topic>` to `completed/discovery/<topic>` | `spec:complete` | In the same completion commit, when this spec is the last open spec linked to the topic |
| `todo/discovery/<topic>` to `completed/discovery/<topic>` | `discovery:approve` | The topic ends with no tickets, so no spec will ever move it |

```bash
mkdir -p docs/specs/completed
git mv docs/specs/todo/<spec-name> docs/specs/completed/<spec-name>
guard spec-index
git add docs/specs/INDEX.md
```

Paths and launch commands inside an old `goal-prompt.md` go stale after a move. That is fine: the run that used them is over, and the next run gets a fresh `goal-prompt.md`.

## Who writes each file

| File | Written by | Read by |
|------|------------|---------|
| `discovery.md` | `discovery:create` | `discovery:approve` |
| `<feature>.md` | Feature Forge, run by `discovery:create` or `spec:create` | `discovery:create`, `spec:create` |
| `synthesis.md` | `discovery:approve` (Step 0) | `discovery:approve` |
| `overview.md` | `spec:create`; `spec:complete` appends the completion report | Plan subagents, the goal run, reviewers, `spec:complete` |
| `implementation-plan.md` | `spec:create`; `ticket:complete` updates rows; the goal run appends Proposed tracker changes and open questions; `spec:review` and `spec:complete` add fix tickets | The goal run, the ticket commands, `spec:complete` |
| `goal-prompt.md` | `spec:create`; `spec:review` and `spec:complete` write a fresh one for fix tickets | `/goal` |
| `review/metrics.md` | `guard metrics` | Reviewers |
| `review/<reviewer>.md` | That reviewer subagent | The main session |
| `review/repro/` | The main session, from verifier reports | Recheck |
| `review/rollup.md` | `guard rollup` | The owner, `guard gate`, `spec:complete` |
| `review/pr-feedback-<round>.md` | `spec:complete` | The owner, recheck, `guard gate` |
| `INDEX.md` | `guard spec-index` | `spec:create` |

## When not to use this layout

- Feature Forge run on its own, outside a command, keeps saving to its own `specs/` folder. Only the discovery and spec commands pass it a topic folder.
- Notes that belong to no spec or topic (roadmaps, ideas) stay outside the specs root, so the index never mistakes them for topics.
